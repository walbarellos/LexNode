## 2024-10-27 - Consistent Affordances on Interactive Cards
**Learning:** When using full elements (like `<article>`) as clickable cards for both mouse and keyboard users, two things are essential: 1) they must have `role="button"` for screen readers to recognize them properly, and 2) the interaction boundaries must be unified. In this app, one card allowed keyboard activation on the full card but restricted mouse clicks to a small inner span, confusing mouse users.
**Action:** Always ensure that when `tabindex="0"` and keyboard events are added to a card, the `onclick` handler and visual hover states (like `hover:bg-gray-50`) apply to the same outer element, and always include `role="button"`.

## 2024-10-27 - Fully Clickable Cards vs Accessibility Anti-patterns
**Learning:** Making entire UI cards (like `<article>` or `<li>`) clickable by blindly adding `role="button"` to the outer wrapper is a massive accessibility anti-pattern, because it forces screen readers to treat the entire complex content block as a single button label, overriding its internal semantics (headings, lists, links are ignored).
**Action:** Instead, implement the pseudo-element overlay CSS pattern: keep the semantic `<button>` inside the card, apply `position: relative` to the card wrapper, and add `::before { content: ''; position: absolute; inset: 0; }` to the button so its clickable area stretches to cover the entire card. Ensure any independent links inside the card get a higher `z-index` (e.g. `position: relative; z-index: 2;`) to remain clickable above the overlay.
